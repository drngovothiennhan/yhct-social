# Beta 2.0 RC Preview Delivery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver exact `release/v1.0` as non-production Vercel previews for the public app and ACC, verify both surfaces, and prepare a controlled draft promotion path to `main` without changing production Firebase/Vercel aliases.

**Architecture:** Add one GitHub Actions workflow dedicated to `release/v1.0`. It deploys both existing Vercel projects without `--prod`, uses the already-approved Vercel token, preserves the production Firebase/WIF trust boundary, captures preview URLs, and smoke-tests each URL. The workflow must never deploy Firebase rules, never promote an alias, and never perform recovery cutover.

**Tech Stack:** GitHub Actions, Node.js 22.16.0, Vercel CLI 59.10.0, Next.js App Router, Firebase client configuration, Vercel OIDC/WIF for ACC runtime.

**Spec:** `docs/superpowers/specs/2026-09-05-beta-2-module-d-backup-recovery-design.md`

## Global Constraints

- Production `main` remains unchanged during RC delivery.
- Vercel RC commands MUST omit `--prod`.
- Firebase production rules/indexes MUST NOT be deployed from `release/v1.0`.
- No service-account JSON, Firebase token, refresh token, or private key may be introduced.
- ACC uses the existing approved Vercel OIDC/WIF identity variables.
- Recovery provider configuration remains server-only; missing provider-specific location/bucket must degrade safely rather than block the ACC shell.
