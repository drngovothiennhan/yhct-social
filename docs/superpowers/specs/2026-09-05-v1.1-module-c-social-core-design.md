# YHCT Social v1.1 — Module C Social Core Consolidation

## Scope

Module C eliminates the dual social architecture that exists after the v1.0 production merge and restores the YHCT-specific publishing capabilities from the earlier Stage 1–3 implementation into the active Module B portal without creating a third content model.

Module C delivers six independently testable areas:

1. One canonical social-post contract for ordinary posts, club news, activity updates, clinical cases, remedies, and Q&A.
2. YHCT-specific composer and post rendering in the active portal.
3. Practitioner verification and clinical de-identification enforcement in domain validation and Firestore rules.
4. Nested comments to depth 3 inside the canonical `posts/{postId}/comments` subtree.
5. Backward-compatible normalization for existing Module B documents plus explicit legacy-v1 detection/audit.
6. Removal of orphaned duplicate client social code only after active routes no longer depend on it.

Module C does not add AI, direct messaging, push notifications, video transcoding, payments, recommendation ranking, or destructive bulk rewrites of production post data.

## Baseline and branch policy

Production baseline: `main@031a347499ea29330f800c0254437337a46376e0`.

Integration baseline: `release/v1.1` created from the same production SHA.

Implementation branch: `feature/v1.1-module-c-social-core`.

No Module C implementation commit may be written directly to `main`. Module C merges first into `release/v1.1` after CI and rules-contract gates are green. Production promotion remains a separate release decision.

## Problem statement

The v1.0 repository contains two social generations:

- the active portal path uses `components/portal/*`, `lib/domain/social.ts`, nested reactions/comments, `kind`, `visibility`, `text`, and `status: active|hidden|deleted`;
- the earlier YHCT path still exists in `components/feed/*`, `components/comments/*`, `lib/domain/post.ts`, legacy top-level comments, and `status: published|hidden|removed`.

Both generations currently write into the same `posts` collection but with incompatible field sets. `lib/post-service.ts` and `lib/comment-service.ts` therefore expose two parallel APIs, and Firestore rules preserve both validators. Continuing feature work on top of this state would multiply query, rules, testing, and migration complexity.

Module C resolves that split before new product subsystems are added.

## Architectural decision

### Canonical model

The Module B social model remains canonical because it is the active production portal, already uses bounded cursor pagination, nested interaction subcollections, role claims, visibility, soft-delete status, and the current navigation architecture.

The earlier YHCT semantic fields are added as optional canonical fields rather than preserving a separate post type.

### Why not keep two schemas

Keeping both schemas is the fastest short-term option but makes every future feature duplicate feed queries, moderation logic, rules, comment behavior, and UI components. This is rejected.

### Why not rewrite all existing production posts immediately

A destructive in-place migration would simplify the database but creates unnecessary production risk before the exact count and shape of legacy documents is known. Module C therefore normalizes Module B reads in place and only detects/audits Stage 1–3 legacy documents. Any later bulk conversion must be a separate idempotent migration with counts, dry-run, backup/manifest, and post-write verification.

## Canonical post contract

Existing Module B fields remain:

- `authorId: string`
- `authorNameSnapshot: string`
- `authorPhotoSnapshot: string | null`
- `authorRoleSnapshot: 'member' | 'mod' | 'super_mod' | 'admin'`
- `kind: 'member_post' | 'club_news' | 'activity_update'`
- `visibility: 'members' | 'public'`
- `text: string`
- `media: SocialMedia[]`
- `activityId: string | null`
- `reactionCount: number`
- `commentCount: number`
- `edited: boolean`
- `status: 'active' | 'hidden' | 'deleted'`
- `createdAt: Timestamp`
- `updatedAt: Timestamp`

Module C adds:

- `contentType: 'general' | 'clinical_case' | 'remedy' | 'qa'`
- `title: string | null`
- `tags: string[]`
- `professionalLabel: boolean`
- `isDeidentified: boolean`
- `authorProfessionalTitleSnapshot: string | null`
- `authorVerificationSnapshot: 'not_required' | 'unsubmitted' | 'pending' | 'verified' | 'rejected'`

### Field semantics

`kind` answers who/why the item is being published in the club context. `contentType` answers what YHCT content format the body represents. They are intentionally separate dimensions.

`general` content may use `title=null`; the three structured YHCT content types require a non-empty title with a maximum of 180 characters.

`tags` are normalized case-insensitively, maximum 10 items, maximum 40 characters each.

`professionalLabel=true` is allowed only when the author is currently a practitioner whose profile has `verificationStatus='verified'`. The snapshot records display context but is never itself trusted for authorization.

`clinical_case` requires `isDeidentified=true`. Other content types are stored with `isDeidentified=true` so consumers do not need nullable logic.

Existing Module B documents that lack Module C fields normalize in the client domain as:

- `contentType='general'`
- `title=null`
- `tags=[]`
- `professionalLabel=false`
- `isDeidentified=true`
- `authorProfessionalTitleSnapshot=null`
- `authorVerificationSnapshot='not_required'`

This compatibility default is read-only. All new Module C writes use the complete canonical contract.

## Author/profile boundary

`users/{uid}` remains the source of truth for practitioner status and professional title.

A post creation request must derive author snapshots from the authenticated user's current profile. Clients may not claim a verified professional label merely by sending `authorVerificationSnapshot='verified'`.

Firestore rules validate professional labeling against the current user profile at write time. Role authorization remains claim-first and continues to use the Module A hierarchy.

Module C does not grant ordinary members any new rights to edit role, club title, account status, member code, provisioning metadata, or verification outcome.

## Canonical comments

The canonical comment location remains:

`posts/{postId}/comments/{commentId}`

Module C extends each comment with:

- `parentId: string | null`
- `depth: 0 | 1 | 2 | 3`

Existing fields remain:

- `authorId`
- `authorNameSnapshot`
- `authorPhotoSnapshot`
- `text`
- `createdAt`
- `updatedAt`
- `edited`
- `status`

### Reply rules

- root comments use `parentId=null` and `depth=0`;
- replies require an existing parent inside the same post comment subtree;
- reply depth equals `parent.depth + 1`;
- maximum depth is 3;
- deleted comments remain tombstones so descendants do not become orphaned;
- ownership and creation timestamp remain immutable;
- moderator hide/unhide behavior remains claim-gated.

The old top-level `/comments` collection becomes compatibility-only and must receive no new writes from active routes once Module C ships.

## Reactions and counters

Canonical reactions remain:

`posts/{postId}/reactions/{uid}`

with one reaction document per user and allowed values `like|heart|support`.

`reactionCount` and `commentCount` stay server-owned cache placeholders. Public clients do not increment or decrement them directly. Active UI derives live interaction state/count from nested subcollections until a trusted server counter reconciler is introduced.

Legacy `/likes` subcollections are compatibility-only and receive no new active-route writes after Module C.

## Portal UX

The active composer in `components/portal/social-composer.tsx` gains a structured-content mode without changing navigation.

Member users may publish:

- general member post;
- clinical case;
- remedy;
- Q&A.

Moderators additionally retain club news and activity-update publishing.

The composer shows only fields relevant to the selected content type:

- general: text, images, visibility;
- clinical case: title, text, tags, images, mandatory de-identification confirmation, optional professional label if verified;
- remedy: title, text, tags, images, optional professional label if verified;
- Q&A: title, text, tags, images.

The post card renders YHCT content type, title, tags, professional verification context, media, reactions, and comments without exposing private certificate metadata.

## Compatibility boundary

Module C uses two explicit mechanisms rather than fabricating missing media metadata.

### Canonical normalizer

`normalizeSocialPostData()` converts raw Firestore data into the active canonical UI record for:

1. Module C canonical social documents.
2. Existing Module B social documents that have `kind` but lack Module C fields.

It applies the documented Module B compatibility defaults and never performs writes.

### Legacy detector/audit

`detectPostSchema()` classifies a raw post as `module_c`, `module_b`, `legacy_v1`, or `unknown`. Stage 1–3 legacy documents are detected by their `type/title/content/mediaPaths` signature and remain untouched.

Legacy-v1 documents are not coerced into `SocialMedia`, because `mediaPaths` does not contain the durable download URL and dimensions required by the canonical UI contract. If production audit later finds legacy documents that must be surfaced in the active portal, they require a separate audited migration that resolves Storage metadata and verifies counts before any rewrite.

Query services must never guess schema from user-provided values. Module C does not silently rewrite a document during a read.

## Legacy code retirement

The following code is eligible for removal only after replacement coverage exists and repository search confirms no active imports:

- `components/feed/*`
- `components/comments/*`
- `components/interactions/*`
- `lib/domain/post.ts`
- legacy publisher/feed/comment/like functions in `lib/post-service.ts` and `lib/comment-service.ts`

The removal is the final implementation task, not the first. Firestore legacy validators may remain for one release window if needed for old stored documents, but new client writes must route only through the canonical contract.

## Firestore rules

Rules must enforce all Module B protections plus:

1. new canonical writes include the Module C field set;
2. `contentType` is one of the four allowed values;
3. structured YHCT posts require valid title length;
4. tags are bounded;
5. clinical cases require `isDeidentified=true`;
6. `professionalLabel=true` requires the current Firestore user to be a verified practitioner;
7. author professional/verification snapshots equal current profile values on creation;
8. comments validate same-post parent identity and exact depth progression;
9. depth may never exceed 3;
10. ordinary clients cannot write server-owned counters;
11. protected Module A user/provisioning fields remain unchanged.

Existing Module B documents remain readable. Owner updates to pre-Module-C documents must either use a compatibility update rule or be upgraded through an explicit canonical write path; the browser must never be permitted to append arbitrary new privileged fields.

## Storage rules

The canonical Module B storage subtree remains:

`social/posts/{uid}/{postId}/{fileName}`

JPEG, PNG, and WebP only; maximum 10 MiB per file; maximum six images enforced by application/domain logic. Ownership, club-member claim, and password-rotation gates remain unchanged.

Legacy `post-media` support may remain read/delete-compatible for the retirement window but receives no new uploads from active Module C routes.

## Query and indexing model

The primary feed remains reverse chronological and cursor-based. Existing filters by club/member/activity/author remain.

Module C adds optional `contentType` filtering. Required composite indexes are committed only when an actual query requires them. No unbounded collection reads are introduced.

Member and activity discovery behavior from Module B is unchanged.

## Error handling

User-visible errors distinguish:

- authentication required;
- password rotation required;
- unauthorized privileged publishing;
- unverified professional label;
- clinical case not confirmed de-identified;
- invalid title/tags/body;
- invalid or oversized media;
- invalid reply depth/parent;
- transient Firebase/network failure.

Firebase internals, claims payloads, private verification artifacts, certificate paths, and provisioning metadata are never rendered to end users.

## Testing strategy

Module C is developed TDD-first.

Required gates:

- unified social-domain tests for all content types and compatibility defaults;
- professional-label and clinical de-identification tests;
- tag/title validation tests;
- schema-detection tests for Module C, Module B, legacy-v1, and unknown documents;
- nested-comment depth and parent tests;
- Firestore contract tests for canonical post creation and comment replies;
- regression tests proving Module A protected fields remain protected;
- active-portal contract tests proving the composer/card use the canonical API;
- repository contract test proving retired legacy UI/service APIs have no active imports before deletion;
- root `npm run check` green;
- root production build green;
- `admin-portal` check/build green;
- rules/index deployment contract green.

## CI and deployment boundary

Module C targets `release/v1.1`, not `main`.

The existing CI workflow must validate pull requests and `release/v1.1` pushes before integration. Firebase/Vercel production workflows remain `main`-gated and are not broadened merely for Module C development.

If a preview deployment is needed, it must use the existing preview/non-production mechanism rather than production credentials.

No service-account private key, activation credential file, roster export, phone list, certificate file, or other private member artifact may enter the repository.

## Acceptance criteria

Module C is complete when:

- active portal routes use one canonical post/comment/reaction model;
- ordinary members can publish general, clinical-case, remedy, and Q&A content through the active composer;
- verified practitioners can use the professional label and unverified users cannot;
- clinical cases cannot be published without the de-identification confirmation;
- canonical comments support replies to depth 3 with tombstone deletion;
- existing Module B posts still render through compatibility defaults;
- Stage 1–3 legacy documents can be detected/audited without destructive writes or fabricated media metadata;
- no active route writes legacy top-level comments, legacy likes, or legacy post-media paths;
- duplicate legacy UI/domain code is removed only after import/reference checks are green;
- Firestore and Storage rules independently enforce the model;
- public app check/build and ACC check/build are green;
- integration CI is green on `release/v1.1` after merge.

## Deferred work

Still outside Module C:

- AI assistant, semantic search, recommendation ranking, and generated medical advice;
- direct/private messaging;
- push notifications;
- video processing/transcoding;
- trusted server counter reconciliation;
- analytics warehouse;
- payment/membership billing;
- destructive bulk conversion of legacy production posts unless a later audited migration explicitly requires it.
